# LightAgent 项目的 `run` 函数相关同步/异步架构设计

本文基于当前代码分析以下符号之间的关系：

- `LightAgent.run()`
- `LightAgent.arun()`
- `LightAgent.astream()`
- `LightAgent._core_run_logic()`
- `LightAgent._run_non_stream_logic()`
- `LightAgent._run_stream_logic()`
- `run_async_safely()`
- `AsyncToolDispatcher.dispatch()`


---

## 一、先给出结论

当前 LightAgent 不是“全链路异步”架构，而是：

> **同步核心执行链 + 异步工具调度能力 + 同步/异步双向适配层。**

它的主要方向是：

```text
异步调用者
    │
    │ await agent.arun(...)
    ▼
asyncio.to_thread(...)
    │
    ▼
同步核心 agent.run(...)
    │
    │ run_async_safely(...)
    ▼
异步工具调度 AsyncToolDispatcher.dispatch(...)
```

因此，两个线程/事件循环桥接函数的职责不同：

| 函数 | 方向 | 解决的问题 |
|---|---|---|
| `asyncio.to_thread()` | 异步 → 同步 | 异步调用者如何运行同步阻塞的 `run()`，同时避免阻塞自己的事件循环 |
| `run_async_safely()` | 同步 → 异步 | 同步 `run()` 如何执行异步的工具调度协程 |

这套设计主要是逐步演化出来的兼容型架构，而不是项目一开始就规划好的全异步架构。

---

## 二、当前代码中的主要角色

### 1. `run()`：同步主入口

定义位置：[`core.py` 的 `LightAgent.run()`](../LightAgent/core.py)

它负责：

1. 校验运行参数；
2. 建立 trace、session 和运行上下文；
3. 执行 hooks、guardrails 和工具准备；
4. 发起第一轮模型请求；
5. 把第一轮响应交给 `_core_run_logic()`；
6. 根据 `stream` 和 `result_format` 返回字符串、结果对象或同步生成器。

它的签名是普通同步函数：

```python
def run(...):
    ...
```

因此，调用：

```python
result = agent.run("hello")
```

调用者会同步等待整个运行完成。

非流式情况下，`run()` 最终返回字符串或 `RunResult`。流式情况下，`run()` 返回一个同步生成器，真正的流式处理在调用者迭代生成器时继续执行。

---

### 2. `arun()`：异步调用入口

定义位置：[`core.py` 的 `LightAgent.arun()`](../LightAgent/core.py)

当前实现：

```python
async def arun(self, query: str, **kwargs: Any) -> Any:
    stream = bool(kwargs.get("stream", False))
    if not stream:
        return await asyncio.to_thread(self.run, query, **kwargs)
    return self.astream(query, **kwargs)
```

非流式时：

```text
await agent.arun(...)
    └── await asyncio.to_thread(agent.run, ...)
```

`arun()` 本身运行在调用方的事件循环中，但同步的 `run()` 被放入线程池执行。这样，调用方事件循环不会直接执行同步模型客户端、同步工具或同步 Agent 主循环。

流式时，`arun()` 不直接执行 `run()`，而是返回异步生成器 `astream()`：

```text
await agent.arun(stream=True)
    └── agent.astream(...)
```

严格地说，异步生成器对象的创建本身不会开始完整运行；真正的执行发生在调用者执行：

```python
async for item in agent.astream(...):
    ...
```

时。

---

### 3. `astream()`：把同步生成器适配成异步生成器

定义位置：[`core.py` 的 `LightAgent.astream()`](../LightAgent/core.py)

当前实现的核心结构：

```python
async def astream(self, query: str, **kwargs: Any) -> AsyncGenerator[Any, None]:
    options = dict(kwargs)
    options["stream"] = True

    stream_result = await asyncio.to_thread(self.run, query, **options)
    sentinel = object()
    try:
        while True:
            chunk = await asyncio.to_thread(next, stream_result, sentinel)
            if chunk is sentinel:
                return
            yield chunk
    finally:
        close = getattr(stream_result, "close", None)
        if callable(close):
            await asyncio.to_thread(close)
```

它做了两类线程隔离：

1. `to_thread(self.run, ...)`：在线程中调用同步 `run()`，取得同步生成器；
2. `to_thread(next, stream_result, sentinel)`：每次在工作线程中推进同步生成器；
3. `to_thread(close)`：异步生成器被取消或结束时，在线程中关闭同步生成器。

因此，`astream()` 不是把 `_run_stream_logic()` 改写成原生异步逻辑，而是给已有的同步流式生成器加了一层异步外壳。

---

### 4. `_core_run_logic()`：同步分流器

定义位置：[`core.py` 的 `_core_run_logic()`](../LightAgent/core.py)

实现逻辑：

```python
def _core_run_logic(self, response, stream, max_retry, max_tool_iterations):
    if stream:
        return self._run_stream_logic(
            response,
            max_retry,
            max_tool_iterations,
        )
    else:
        return self._run_non_stream_logic(response, max_retry)
```

它本身不是异步函数，也不创建线程。它只根据 `stream` 选择两个同步实现之一：

```text
stream=False ──► _run_non_stream_logic()
stream=True  ──► _run_stream_logic()
```

因此，`_core_run_logic()` 是一个**同步内部路由节点**，不是同步/异步转换节点。

---

### 5. `_run_non_stream_logic()`：非流式工具循环

定义位置：[`core.py` 的 `_run_non_stream_logic()`](../LightAgent/core.py)

它处理：

1. 模型返回普通文本；
2. 模型返回一个或多个 tool calls；
3. 顺序执行工具；
4. 把工具结果追加到消息历史；
5. 再次调用模型；
6. 重复上述过程，直到模型返回最终文本或达到重试上限。

简化后的调用关系是：

```text
run(stream=False)
    │
    ▼
_core_run_logic(stream=False)
    │
    ▼
_run_non_stream_logic()
    │
    ├── 没有 tool_calls
    │       └── 返回最终回复
    │
    └── 有 tool_calls
            ├── 解析参数和执行前检查
            ├── run_async_safely(dispatch(...))
            ├── 记录工具结果
            ├── 再次调用模型
            └── 回到循环开始
```

工具调用的关键代码形态是：

```python
tool_response = run_async_safely(
    self.tool_dispatcher.dispatch(
        function_call.name,
        function_args,
    )
)
```

注意：`_run_non_stream_logic()` 自身是同步函数，但调用的是异步的 `dispatch()`。

---

### 6. `_run_stream_logic()`：同步流式生成器

定义位置：[`core.py` 的 `_run_stream_logic()`](../LightAgent/core.py)

它是同步生成器：

```python
def _run_stream_logic(...) -> Generator[str, None, None]:
    ...
    yield chunk
```

它执行的主要过程是：

```text
读取模型同步流
    │
    ├── yield 每个模型 chunk
    ├── 累积文本和 tool call 参数
    ├── 当前模型响应结束后判断是否有工具调用
    │
    ├── 没有工具调用
    │       └── 完成运行
    │
    └── 有工具调用
            ├── yield 工具调用信息
            ├── run_async_safely(dispatch(...))
            ├── 消费同步工具生成器（如果有）
            ├── 组织 tool 消息
            ├── 再发起下一轮同步模型流
            └── 继续 yield
```

流式工具调用处同样使用：

```python
tool_response = run_async_safely(
    self.tool_dispatcher.dispatch(tool_name, function_args)
)
```

所以“流式”主要是输出协议和生成器消费方式发生变化，并不意味着内部所有执行都变成了异步执行。

---

### 7. `run_async_safely()`：同步内部调用异步工具的桥

定义位置：[`core.py` 的 `run_async_safely()`](../LightAgent/core.py)

逻辑可以概括为：

```python
try:
    asyncio.get_running_loop()
except RuntimeError:
    return asyncio.run(coro)

with ThreadPoolExecutor(max_workers=1) as executor:
    future = executor.submit(asyncio.run, coro)
    return future.result()
```

它分成两种情况。

#### 当前线程没有运行中的事件循环

```text
同步 run() 所在线程
    └── asyncio.run(dispatch(...))
            └── 创建事件循环
            └── await dispatch()
            └── 返回结果
```

这是在普通同步调用 `agent.run()` 时最常见的路径。

#### 当前线程已经有运行中的事件循环

```text
当前线程：已有事件循环
    │
    │ 不能直接 asyncio.run()
    ▼
ThreadPoolExecutor 工作线程
    │
    └── asyncio.run(dispatch(...))
            └── 工作线程拥有独立事件循环
```

然后当前线程执行：

```python
future.result()
```

等待工作线程完成。

因此，这个函数解决的是 `asyncio.run()` 嵌套冲突，但它仍然是同步等待模式，不是非阻塞调用。

---

### 8. `AsyncToolDispatcher.dispatch()`：异步调度器，不代表所有工具都是异步的

定义位置：[`tools.py` 的 `AsyncToolDispatcher.dispatch()`](../LightAgent/tools.py)

它的函数签名是：

```python
async def dispatch(self, tool_name, tool_params):
```

但它内部可以调度四种工具：

| 工具类型 | `dispatch()` 的行为 |
|---|---|
| 普通同步函数 | 直接调用 `tool_call(**tool_params)` |
| 异步函数 | `await tool_call(**tool_params)` |
| 同步生成器函数 | 返回同步 `Generator`，由调用方消费 |
| 异步生成器函数 | 在 `dispatch()` 内收集全部结果，再序列化为字符串 |

伪代码：

```python
if inspect.iscoroutinefunction(tool_call):
    result = await tool_call(**tool_params)
elif inspect.isasyncgenfunction(tool_call):
    chunks = [chunk async for chunk in tool_call(**tool_params)]
    result = ...
elif inspect.isgeneratorfunction(tool_call):
    return tool_call(**tool_params)
else:
    result = tool_call(**tool_params)

return self._serialize_result(result)
```

这里有一个重要区别：

> `dispatch()` 是异步函数，只说明“调度器可以被 await”，不说明它调用的每个工具都在异步执行。

普通同步工具在 `dispatch()` 内直接调用。如果这个同步工具本身执行耗时 I/O 或 CPU 密集计算，它会阻塞承载 `dispatch()` 的事件循环，除非更外层已经把整个 `run()` 放进了线程。

---

## 三、非流式调用链

### 场景 A：同步调用者调用 `run()`

调用：

```python
result = agent.run("分析这个问题")
```

完整主链可以表示为：

```text
调用者同步线程
    │
    ▼
LightAgent.run()
    │
    ├── 参数、session、hooks、guardrails
    ├── 首轮同步模型请求
    │
    ▼
_core_run_logic(stream=False)
    │
    ▼
_run_non_stream_logic()
    │
    ├── 模型无 tool_calls
    │       └── 返回最终文本
    │
    └── 模型有 tool_calls
            │
            ▼
        run_async_safely(
            AsyncToolDispatcher.dispatch(...)
        )
            │
            ├── 通常：asyncio.run()
            └── 特殊情况：另开线程执行 asyncio.run()
            │
            ▼
        工具结果
            │
            ▼
        再次同步模型请求
            │
            └── 循环直到完成
```

这里的“异步”主要发生在工具调度内部，但整个 `run()` 对调用者仍然是阻塞的。

### 场景 B：异步调用者调用 `arun()`，非流式

调用：

```python
result = await agent.arun("分析这个问题")
```

主链：

```text
调用方事件循环
    │
    ▼
LightAgent.arun()
    │
    ▼
await asyncio.to_thread(self.run, ...)
    │
    ▼
线程池工作线程
    │
    ▼
LightAgent.run()
    │
    ▼
_core_run_logic(False)
    │
    ▼
_run_non_stream_logic()
    │
    ▼
run_async_safely(dispatch(...))
    │
    └── 通常在该工作线程中 asyncio.run(dispatch(...))
```

这个场景中，`to_thread()` 已经把 `run()` 移到了一个没有运行中事件循环的工作线程。因此 `run_async_safely()` 通常会直接走 `asyncio.run()` 分支，而不会再额外创建第二个线程。

常见的实际结构是：

```text
调用方事件循环
    └── to_thread()
            └── 工作线程执行 run()
                    └── asyncio.run()
                            └── dispatch()
```

## 四、流式调用链

### 场景 A：同步调用者调用 `run(stream=True)`

调用：

```python
for item in agent.run("分析这个问题", stream=True):
    print(item)
```

主链：

```text
agent.run(stream=True)
    │
    ├── 同步完成准备工作
    ├── 首轮模型请求
    │
    └── 返回同步生成器
            │
            ▼
        迭代生成器
            │
            ▼
        _run_stream_logic()
            │
            ├── for chunk in response
            │       └── yield chunk
            │
            ├── 发现工具调用
            │       ├── yield 工具调用信息
            │       ├── run_async_safely(dispatch(...))
            │       ├── 消费同步工具生成器
            │       └── 再发起模型流请求
            │
            └── 继续 yield，直到结束
```

同步调用者在每次 `next()` 时都会等待下一块结果。

### 场景 B：异步调用者调用 `astream()`

调用：

```python
async for item in agent.astream("分析这个问题"):
    print(item)
```

主链：

```text
调用方事件循环
    │
    ▼
astream()
    │
    ├── await to_thread(self.run, stream=True)
    │       └── 工作线程执行 run()
    │               └── 得到同步生成器
    │
    ├── await to_thread(next, stream_result, sentinel)
    │       └── 工作线程推进 _run_stream_logic()
    │               ├── 读取同步模型流
    │               ├── yield 模型 chunk
    │               └── 可能调用 run_async_safely(dispatch(...))
    │
    ├── await to_thread(next, ...)
    ├── await to_thread(next, ...)
    └── finally: await to_thread(close)
```

每个 chunk 都经过一次“异步等待线程中的同步 `next()`”的适配。

需要注意：`_run_stream_logic()` 的模型流迭代是同步的；`astream()` 只是把每次推进放入线程池，因此它是**异步可消费的同步流适配器**。

## 五、同步、异步和阻塞点逐层分析

### 1. `await asyncio.to_thread(...)` 是否阻塞？

对调用方事件循环来说，它通常是非阻塞等待：

```python
await asyncio.to_thread(self.run, ...)
```

同步工作在线程池中执行，调用方事件循环可以继续调度其他任务。

但当前这个协程任务本身仍然要等待线程返回结果。它不是“立即返回”，只是：

```text
等待期间不占住事件循环线程
```

### 2. `future.result()` 是否阻塞？

是：

```python
return future.result()
```

它会阻塞当前线程，直到异步工具完成。

如果 `run_async_safely()` 在事件循环线程中被直接调用，那么这个事件循环线程会被阻塞。当前项目的 `arun()` 非流式路径通常先用 `to_thread()` 把 `run()` 移走，所以常见路径不会阻塞调用方事件循环；但直接在异步函数中调用同步 `agent.run()` 仍可能阻塞事件循环。

### 3. `dispatch()` 中的同步工具是否阻塞？

可能阻塞。

例如：

```python
async def dispatch(...):
    result = tool_call(**tool_params)
```

如果 `tool_call` 是普通同步函数，并且内部执行长时间 I/O 或计算，它会阻塞当前事件循环。

不过在当前常见调用路径中：

```text
arun()
    └── to_thread(run)
            └── run_async_safely()
                    └── asyncio.run(dispatch())
```

这个事件循环本身位于工作线程中，所以阻塞的是工作线程里的临时事件循环，而不是调用方事件循环。

### 4. `_run_non_stream_logic()` 是否阻塞？

是。它是同步循环，会顺序等待：

- 模型请求；
- 工具执行；
- 再次模型请求；
- hooks、guardrails 和序列化。

### 5. `_run_stream_logic()` 是否阻塞？

在同步语义上是阻塞的。它只有在 `yield` 时把控制权交给生成器消费者；推进下一项时，可能继续等待：

- 同步模型流的下一个 chunk；
- 工具执行；
- 工具生成器的下一个 chunk；
- 下一轮模型请求。

当它被 `astream()` 通过 `to_thread(next, ...)` 推进时，这些阻塞被限制在线程池工作线程中。

### 6. 异步工具本身是否一定不阻塞？

不一定。

如果异步工具内部使用了真正的异步 I/O，例如异步 HTTP 客户端，那么它可以让自己的事件循环在等待 I/O 时运行其他任务。

但如果工具虽然声明为 `async def`，内部却直接调用阻塞 API，例如同步 HTTP 客户端或长时间 CPU 计算，那么它仍可能阻塞事件循环。

“函数写成 `async def`”和“执行过程不会阻塞”不是同一件事。

## 六、这套结构为什么会出现？

从 Git 历史看，它明显是逐步演化而来的。

### 1. 原始重心是同步 `run()`

项目早期以同步 Agent 主循环为核心。同步模型客户端、同步工具和同步生成器都可以直接使用。

异步工具支持是后来加入到同步主循环中的能力，早期做法是直接：

```python
asyncio.run(self.tool_dispatcher.dispatch(...))
```

### 2. `run_async_safely()` 是针对嵌套事件循环问题的修复

提交 [`4c7d836`](https://github.com/wanxingai/LightAgent/commit/4c7d836) 的提交信息是：

```text
fix: handle nested event loop in tool dispatch
```

该改动针对 FastAPI、Jupyter 和其他异步宿主环境中直接调用 `asyncio.run()` 会失败的问题，引入了 `run_async_safely()`。

因此它主要是：

```text
同步核心已经存在
    ↓
真实环境出现嵌套事件循环错误
    ↓
增加线程隔离桥接
```

并非最初的整体架构规划。

### 3. `arun()` 和 `astream()` 是后续的兼容性异步入口

在 v0.10 统一运行时相关提交 [`b1106c9`](https://github.com/wanxingai/LightAgent/commit/b1106c9) 中，项目增加了异步入口和运行时能力。

当前文档字符串明确说明，旧版同步模型和工具客户端通过工作线程隔离，以保持兼容：

```text
Sync model and tool clients are isolated in a worker thread for v0.9 compatibility.
```

这说明 `arun()` 的主要策略不是重写同步内核，而是：

```text
保留旧 run()
    ↓
用 asyncio.to_thread() 包装它
    ↓
提供异步调用接口
```

### 4. 后续能力继续增加了原生异步方向

当前 `arun()` 的文档还提到，新的 Native Async Providers 和 Jobs 可以留在调用方的事件循环中。这说明项目正在逐渐出现两条路径：

```text
旧兼容路径：arun() → to_thread(run)
新原生路径：Native Async Provider/Job → 调用方事件循环
```

因此当前架构也可以看成是从“同步优先”向“同步/异步分层”演化过程中的中间状态。

---

## 七、这种 Agent 框架架构是否正常？

### 1. 同时提供 `run()` 和 `arun()` 是正常的

这是 Python 库常见的兼容设计：

```python
agent.run(...)
await agent.arun(...)
```

同步入口适合：

- CLI；
- 普通脚本；
- 同步测试；
- 传统同步插件；
- 不需要并发等待的简单程序。

异步入口适合：

- FastAPI、Starlette 等 Web 服务；
- Jupyter；
- 并发处理多个 Agent 任务；
- 异步模型客户端；
- 异步工具和异步工作流。

### 2. 混合工具类型也是正常的

Agent 工具生态天然混合：

```text
普通函数
异步函数
同步生成器
异步生成器
```

调度器统一提供 `async def dispatch()`，可以让上层用一种方式调用工具，同时在内部兼容多种工具形态。这是实用的框架设计。

### 3. 当前实现属于兼容型、渐进式架构

它的优点：

- 不破坏已有的同步 API；
- 可以接入异步工具；
- 可以在 FastAPI/Jupyter 等已有事件循环环境中使用；
- 同步和异步工具可以共存；
- 可以逐步引入原生异步 Provider 和 Job。

它的代价：

- 线程切换和临时事件循环带来额外开销；
- `future.result()` 仍然是同步等待；
- 取消传播和超时控制跨线程时更复杂；
- 部分异步资源可能绑定特定事件循环，不能随意跨线程使用；
- 流式输出要通过同步生成器和 `to_thread(next, ...)` 适配；
- 旧同步核心无法充分利用全链路异步 I/O 的并发优势。

因此，这种设计“正常”，但更准确的评价是：

> **它是一个合理的兼容型过渡架构，而不是最终形态的纯异步架构。**

## 八、和理想的全异步架构对比

当前 LightAgent 更接近：

```text
同步核心架构
    ├── run()
    └── arun() 通过 to_thread() 包装 run()
```

另一种更彻底的长期架构是：

```text
异步核心架构
    ├── arun() 是真正的核心执行路径
    └── run() 只作为同步兼容入口，桥接到 arun()
```

理想的异步核心可能是：

```python
async def arun(...):
    response = await async_model_client(...)
    tool_result = await dispatch(...)
    ...

def run(...):
    return run_async_safely(arun(...))
```

但这个迁移会涉及：

- 模型客户端；
- 工具调用；
- hooks；
- guardrails；
- Session；
- trace；
- 流式协议；
- LightSwarm handoff；
- 取消和超时；
- 兼容旧版同步工具。

因此项目先保留同步核心，再增加 `arun()`，是一个风险更低、兼容性更好的工程选择。

## 九、最终调用关系总图

### 非流式：同步入口

```text
agent.run()
    ├── 首轮同步模型请求
    └── _core_run_logic(False)
            └── _run_non_stream_logic()
                    ├── 无工具调用 → 返回最终结果
                    └── 有工具调用
                            └── run_async_safely(
                                    AsyncToolDispatcher.dispatch(...)
                                )
                                    ├── 无运行中 loop
                                    │     └── asyncio.run(dispatch)
                                    └── 已有运行中 loop
                                          └── 新线程 + asyncio.run(dispatch)
```

### 非流式：异步入口

```text
await agent.arun()
    └── await asyncio.to_thread(agent.run)
            └── 同步 run()
                    └── _run_non_stream_logic()
                            └── run_async_safely(dispatch())
```

### 流式：同步入口

```text
agent.run(stream=True)
    └── 返回同步生成器
            └── _run_stream_logic()
                    ├── 同步迭代模型流
                    ├── yield chunk
                    ├── run_async_safely(dispatch())
                    └── 再次请求模型并继续 yield
```

### 流式：异步入口

```text
async for item in agent.astream()
    ├── await to_thread(agent.run, stream=True)
    ├── await to_thread(next, stream_result)
    │       └── 推进 _run_stream_logic()
    ├── await to_thread(next, stream_result)
    └── finally: await to_thread(close)
```

最值得记住的四句话是：

1. `run()` 是当前同步核心；
2. `arun()` 用 `asyncio.to_thread()` 把同步核心移出调用方事件循环；
3. `_run_non_stream_logic()` 和 `_run_stream_logic()` 都是同步实现；
4. `run_async_safely()` 让同步核心可以等待异步工具调度，但本身仍然可能阻塞等待。
