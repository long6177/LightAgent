# 异步生成器工具的价值与边界

本文总结对 LightAgent 工具调度中异步生成器的理解，重点回答两个问题：

1. 异步生成器相比普通异步函数，解决了什么问题？
2. 什么情况下异步生成器真的能带来“更早消费结果”的收益？

相关实现位于 [`AsyncToolDispatcher.dispatch()`](../LightAgent/tools.py)。

---

## 一、先给出结论

普通异步函数适合：

> 异步地完成一次 I/O，最后返回一个完整结果。

异步生成器适合：

> 异步地获取会分段产生的数据，并在每一段到达后交给下游消费。

不过，异步生成器要真正实现端到端的实时处理，还必须满足第二个条件：

> 调用链支持逐段消费。

因此，判断是否应该使用异步生成器，不能只看“这个工具是否使用了异步 I/O”，还要看：

```text
结果是否天然会分段产生？
        +
调用方是否支持逐段消费？
```

只有这两个条件同时成立，异步生成器的流式价值才会完整体现出来。

---

## 二、普通异步函数解决什么问题

普通异步函数适合一次性得到完整结果的工具：

```python
async def get_weather(city: str) -> dict:
    response = await weather_api.get(city)
    return response
```

调用方通常这样使用：

```python
weather = await get_weather("Beijing")
```

执行过程是：

```text
等待异步 I/O 完成
        ↓
得到完整结果
        ↓
交给 Agent 或模型
```

典型场景包括：

- 查询天气；
- 查询一个用户；
- 请求一个 API；
- 执行一次数据库查询；
- 下载一个需要完整读取后才能解析的文件。

这里即使内部使用了异步 I/O，调用者关心的仍然是一个最终结果，所以普通异步函数就足够了。

---

## 三、异步生成器增加了什么能力

异步生成器同时具备 `async` 和 `yield`：

```python
async def stream_events():
    for i in range(3):
        event = await wait_for_next_event()
        yield event
```

它不是返回一个完整结果，而是返回一个 `AsyncGenerator`。调用方通过 `async for` 消费：

```python
async for event in stream_events():
    consume(event)
```

执行过程变成：

```text
收到第 1 段 → 立即消费
收到第 2 段 → 立即消费
收到第 3 段 → 立即消费
```

这与下面的普通异步函数不同：

```python
async def get_all_events():
    events = []
    for i in range(3):
        events.append(await wait_for_next_event())
    return events
```

后者必须等全部事件到达后，调用方才能获得结果。

---

## 四、为什么 Agent 场景会需要它

Agent 相关业务中，有些结果不是“等全部完成后再处理”最合适，而是希望尽早进入下游流程。例如：

- 实时搜索多个数据源；
- 读取长连接或 SSE 事件；
- 监听日志或消息队列；
- 分页读取大量远程数据；
- 逐步产生模型输出；
- 将已发现的结果交给过滤器、排序器或界面。

### 示例：实时搜索多个数据源

```python
async def search_news(query: str):
    async for article in news_api.stream_search(query):
        yield article
```

调用方可以在搜索尚未完全结束时处理已经到达的文章：

```python
async for article in search_news("Python"):
    display_article(article)
```

这里的价值不是“最终结果不同”，而是：

```text
降低首个结果的等待时间
避免必须一次性缓存所有结果
允许下游提前开始工作
```

例如，第一个数据源已经返回文章时，界面就可以展示它；不必等其他数据源全部搜索结束。

---

## 五、“结果着急”还不够

“希望尽快看到结果”是动机，但不是充分条件。还必须满足以下三个条件：

### 1. 数据源支持分段读取

如果远程 API 只有在计算完成后才返回完整 JSON，那么调用方无法凭空得到中间结果。

### 2. 每一段结果具有独立消费价值

如果只有完整文件才能解析，那么逐块拿到的数据可能没有实际用途。

### 3. 下游支持流式协议

生产者使用了异步生成器，并不代表结果就会自动被实时消费。下游必须支持：

```python
async for chunk in producer():
    ...
```

或者使用异步队列、事件总线等类似机制。

因此更准确的判断公式是：

```text
异步生成器的价值
    =
分段产生的结果
    ×
逐段消费的调用链
```

任一部分为零，端到端的流式收益就无法实现。

## 六、四种工具函数的定位

| 工具类型 | 适合的情况 | 结果形态 |
| --- | --- | --- |
| 普通同步函数 | 一次性本地计算或简单处理 | 一个普通值 |
| 普通异步函数 | 一次异步 I/O，最终需要完整结果 | 一个最终值 |
| 同步生成器 | 数据可以分段产生，但不需要异步等待 | `Generator` |
| 异步生成器 | 数据分段产生，且每段之间需要异步 I/O | `AsyncGenerator` |

可以用下面的形式快速判断：

```text
def + return       → 普通同步函数
async def + return → 普通异步函数
def + yield        → 同步生成器
async def + yield  → 异步生成器
```

例如：

```python
def local_results():
    for item in cached_items:
        yield item
```

如果数据已经在内存中，并不需要 `await`，同步生成器更自然。

而下面的工具需要等待远程数据逐段到达：

```python
async def remote_results():
    async for item in remote_stream():
        yield item
```

这才是异步生成器的典型场景。

## 七、LightAgent 当前实现的边界

当前 `dispatch()` 对四种工具的处理方式如下：

```python
if inspect.iscoroutinefunction(tool_call):
    result = await tool_call(**tool_params)
elif inspect.isasyncgenfunction(tool_call):
    chunks = [chunk async for chunk in tool_call(**tool_params)]
    result = chunks[0] if len(chunks) == 1 else "".join(str(c) for c in chunks)
elif inspect.isgeneratorfunction(tool_call):
    return tool_call(**tool_params)
else:
    result = tool_call(**tool_params)
```

对应关系是：

| 工具类型 | `dispatch()` 的行为 |
| --- | --- |
| 普通同步函数 | 直接调用，然后序列化 |
| 普通异步函数 | `await` 后得到最终结果 |
| 同步生成器 | 透传 `Generator`，由调用方消费 |
| 异步生成器 | 在 `dispatch()` 内部全部消费，再合并为结果 |

异步生成器分支的核心代码是：

```python
chunks = [chunk async for chunk in tool_call(**tool_params)]
```

这意味着异步生成器虽然在工具内部可以逐段读取异步数据，但当前 `dispatch()` 会先收集全部 chunk，再向上层返回。

因此，当前 LightAgent 中需要区分两种能力：

```text
异步生成器本身的能力：
    可以异步地逐段产生结果

当前 dispatch() 的端到端能力：
    收集完所有结果后再返回
```

换句话说，当前实现保留了异步生成器的内部表达能力，但暂时没有把它转换成完整的端到端异步流式输出。

相比之下，同步生成器会被直接透传，因此当前调用链对同步生成器的逐块消费支持更直接。

---

## 八、异步生成器当前仍然有价值吗

有，但价值需要准确描述。

当前实现中，异步生成器仍然可以：

- 封装异步分页或异步流式读取逻辑；
- 避免工具内部必须一次性组织所有数据；
- 让工具实现贴近数据源的自然接口；
- 在未来支持异步流式调用时保留扩展空间。

但它当前不能带来完整的实时收益：

- chunk 不会在 `dispatch()` 中逐个透传到上层；
- 模型工具消息仍然需要一个最终字符串；
- 如果工具永远不结束，`dispatch()` 也无法返回最终结果。

所以在当前 LightAgent 中，异步生成器更接近：

```text
内部异步迭代
    +
dispatch() 内部汇总
    =
最终一次性工具结果
```

---

## 九、最终理解

可以把普通异步函数和异步生成器分别记成：

```text
普通异步函数：
    异步地等待一个完整结果

异步生成器：
    异步地等待，并逐段产生结果
```

但要实现“来一段就立刻拿去消费”，还必须满足：

```text
数据源能够分段产生
        +
调用链能够逐段消费
```

因此最准确的总结是：

> 普通异步 I/O 通常使用普通异步函数；当 I/O 结果天然会分段产生，并且下游希望每段到达后立即处理时，才适合使用异步生成器。异步生成器是否真正有实时价值，不只取决于工具函数本身，还取决于整个调用链是否支持流式传递。
